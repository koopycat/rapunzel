rapunzel

Give the coding agent one project and nothing else.

rapunzel runs pi, Claude Code, Codex, dsh, and opencode in a hardened Docker container. The agent gets the project it works on, its own state, and the network access you choose. Your home directory, SSH keys, and other projects stay outside.

Rapunzel’s tower has one way out, and you hold the strand.

Docker enforces the boundary, not the agent.

rapunzel doesn’t rely on the agent’s own permission prompts or sandbox. The launcher, Docker, and the sidecar enforce every rule, whichever harness runs inside. Open any claim to see how it works.

It sees one directory.The project, mounted read-write at /workspace. Nothing else from your machine.

The only host bind mount is the project. Your home directory, ~/.ssh, the harnesses’ own host folders such as ~/.pi or ~/.claude, and the Docker socket are never mounted. No ports are published, except dsh’s web UI on 127.0.0.1 in open mode.

Architecture 4.1

It runs without root.Your own user ID, every Linux capability dropped.

The container starts with --user set to your UID and GID, --cap-drop=ALL, and no-new-privileges, so setuid binaries can’t raise it. libnss-wrapper names the UID agent without root, and files it creates in the project belong to you.

Architecture 4.2

It gets only the variables you allow.No inherited host environment, no injected loader hooks.

Only allowlisted names enter: known provider keys, proxy settings, and the profile’s own names. A denylist (LD_PRELOAD, NODE_OPTIONS, BASH_ENV, PATH, …) beats everything, and env files go through the same filter. Secrets arrive at runtime, never in the image.

Architecture 4.4

The network fails closed.In the restricted modes, ignoring the proxy leads nowhere.

The agent sits alone on a per-run Docker --internal network in isolated gateway mode: no route out, no external DNS, no host address. Its one peer is the sidecar, which reaches the internet through its own per-run bridge, never Docker’s default one. This needs Docker Engine 28 or newer.

Architecture 4.5 · Egress decisions

Allowed means exactly that host.The TLS handshake has to name the host you allowed.

Pipelock checks each tunnel’s host against the allowlist, requires the TLS server name to match it, resolves the name itself, and refuses private, loopback, and metadata addresses. Without the TLS check, an allowed host on a shared CDN would open every other site on it; Squid and Smokescreen failed exactly that test. The allowlist comes only from your host settings, never from files the agent can write.

Decision D4

Your key can stay out of reach.In strict mode only the gateway holds it.

Caddy forwards only /anthropic, /openai, and /custom to fixed upstreams and always overwrites the auth header with the real key. Overwriting matters: the agent can’t use an allowed provider with an attacker’s key to smuggle data out.

Decision D6

Your host’s git can’t be turned against you.Hooks and git config are read-only; other risky files are reported.

The agent can still commit, branch, and stash, but it can’t add a hook, set core.fsmonitor, or move core.hooksPath. Files host tools run on their own, such as .envrc, editor tasks, or package scripts, are hashed before the run and every change is listed when it ends.

Architecture 4.6

Each project keeps its own state.Logins, sessions, and extensions never mix between projects.

Each project and harness gets a named volume, rapunzel-<harness>-<hash>. You log in once per project, not per run, and a poisoned extension in one project can’t follow you into another. Env-file credentials are passed fresh each run and never written to the volume.

Architecture 4.3

Bring the agent you already use.

Every harness runs behind the same launcher with the same controls. Each gets its own image and a shortcut such as rapunzel-claude.

One command, start to finish.

Everything below happens on every rapunzel run, before the agent gets its first token and after it exits.

  1. Pick the profile and projectFrom --harness or the shortcut name. It refuses to run as root.
  2. Load your env file~/.config/rapunzel/<harness>.env if it exists, filtered by the allowlist.
  3. Check DockerExplains how to start an engine, and builds a missing harness image.
  4. Prepare the state volumeHands it to your UID and registers the run under a run ID.
  5. Set up the networkIn a restricted mode: two fresh networks and a healthy sidecar.
  6. Snapshot risky filesHashes .envrc, editor tasks, hooks, manifests, and more.
  7. Run the agentMaps the identity, writes the harness config, starts the harness.
  8. Clean upRemoves the sidecar, networks, and run record, and resets the terminal.
  9. Report changesLists every risky file the agent added, changed, or removed.

What it doesn’t protect you from.

A sandbox you can trust is clear about its edges. These are the residual risks, most serious first.

  1. high
    Risky files outside git. Changes to .envrc, editor tasks, or package scripts are reported, not blocked. Read the report before you run those tools.
  2. high
    Data sent to allowed hosts. The agent can send anything it reads to the hosts it may reach. Every allowed host, including a runtime grant, widens that channel.
  3. medium
    Encrypted Client Hello. With ECH, the outer TLS name could name an allowed host while the inner one names another site on the same CDN. Not yet verified.
  4. medium
    Agent-volume tampering. Extensions, settings, and trust decisions persist and run again next session, within that project.
  5. medium
    Sidecar compromise. A compromised sidecar has full egress, limited to the internet by its own per-run network.
  6. medium
    Unpinned transitive dependencies. pi ships no shrinkwrap, so its dependencies resolve when the image is built.
  7. low
    Kernel or runtime escape. Unlikely but serious: on Linux it reaches the host; on Docker Desktop and Colima, the VM.

Docker Desktop on macOS has shut down twice after the read-only git sub-mounts; Colima and Linux are fine. WSL2 is untested. Limitations and future work

Every claim has a test.

The checks act as a hostile agent through the real launcher, so they test the configuration you actually run. CI runs them on every change, and images are published only after they pass.

verify-isolation.sh

Not root; only /workspace and the volume are writable; no host home, ~/.ssh, or ~/.pi in the mount table.

verify-host-files.sh

Writing hooks and git config fails, a commit still works, and planted .envrc and editor tasks are reported.

verify-egress.sh

No DNS, direct IP, metadata, or host access; wrong or missing TLS names, IP literals, and plain HTTP are refused; the real key never reaches the agent in strict mode.

verify-control.sh

Runtime grants and revokes take effect, TLS checks survive a policy change, and a lost acknowledgement stops egress instead of reporting success.

test.sh

Each harness starts offline through the real entrypoint, with the right identity and no key written to the volume.

test-control.sh

Host-only checks of the run registry, grant validation, and safe output, without Docker.

Tested on Docker Engine 28 (Ubuntu, CI), Colima with Docker Engine 29 (macOS), and Docker Desktop 29 (macOS).

Start in a minute.

You need Docker and jq on the host. The image is published for amd64 and arm64.

# once: put the checkout on PATH and use the published image
export PATH="$HOME/src/rapunzel:$PATH"
export RAPUNZEL_IMAGE=ghcr.io/koopycat/rapunzel

# run pi on the current project
cd ~/src/my-project
rapunzel

# or Claude Code, limited to allowed hosts
RAPUNZEL_EGRESS=allowlist rapunzel-claude

# approve a blocked host from a second terminal
rapunzel-ctl egress pending RUN_ID
rapunzel-ctl egress allow RUN_ID registry.npmjs.org
